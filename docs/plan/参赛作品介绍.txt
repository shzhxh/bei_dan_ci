背单词 55 篇　参赛作品介绍

作品形态：纯静态英语背诵站点。
规模：55 篇短文、3,242 个目标词、62 个页面。
运行成本：0 元。

　　这个网站只解决一件事：把 3,242 个高频英语词写进 55 篇能读、能背的短文，再用一套页面把「读—学—背—测—复习」串起来。没有账号、没有后端、没有付费，构建产物是 62 个静态页面，部署在 GitHub Pages。

　　我没有真实用户量可报，也不编。能被核对的是内容、数据和构建结果。

一、已实现的核心功能与亮点

　　（一）55 篇短文：把「背词表」换成「读故事」

　　　　为什么做：用尽量少的篇目覆盖 3,242 词。

　　　　原来的方式：词表 App 每天背 20–30 个孤立词条，释义、例句、复习分离，背完只记得见过。

　　　　我的做法：主线 50 篇，每篇 59–60 个目标词；补漏 5 篇，每篇 57–58 个。正文 280–320 词、24–28 句，句长 8–14 词，每句 2–4 个目标词，词次密度 18%–22%。一篇一个场景，按时间或因果推进。

　　　　改进在哪：读一篇 300 词的故事，会接触 59–60 个目标词，每词至少出现一次，并带着原句和搭配进入记忆；省掉多工具切换、自己造语境、背完不会用的环节。

　　　　核对结果：主线覆盖 2,953/2,953，补漏 289/289；55 篇共 16,145 词、1,544 句；全局审计 0 错误。

　　（二）双轨路线：同一套内容，两种完成标准

　　　　为什么做：同时服务「全部 3,242 词」和「中考 1,547 词」两类人，不写两套教材。

　　　　原来的方式：另编中考材料，内容翻倍；或让基础弱的人直接面对 55 篇。

　　　　我的做法：一套内容两条路线。完整 55 篇、3,242 词；中考 27 篇 = 主线 p01–p22 + 补漏 b01–b05，覆盖 1,547 词（主线 1,258，81.3%；补漏 289，18.7%）。

　　　　改进在哪：内容只写一遍，路线只是视图和进度统计方式不同。学完 27 篇可停，继续学不用换材料；补漏页标「非星级词」，不计入主线分母。

　　（三）短文页四态：阅读、精讲、背诵 B1–B4、检测 8 题

　　　　为什么做：让一篇从「读过」走到「背下、测过」，不换工具。

　　　　原来的方式：阅读、词表、背诵、检测分散在四类工具，状态互不相通。

　　　　我的做法：每篇四个标签。

　　　　① 阅读：分段正文、译文开关、字号 15–26px、行距可调、点句朗读、点词卡（词性/释义/搭配/发音）。

　　　　② 精讲：目标词表，含词性、释义、搭配；侧栏给篇长、句数、密度、句式模板。

　　　　③ 背诵：B1 逐句跟读与自动连读；B2 首字母挖空，全对才记完成；B3 首字母补全；B4 中文回译。

　　　　④ 检测：8 题，覆盖词义、填空、搭配、听音与理解，自动判分，标正确/错选项，成绩存本地，可重做。

　　　　改进在哪：四态共享正文、词表与进度；B2 即时判定；成绩和阶段落在本地，下次打开知道停在哪。

　　（四）零成本辅助：浏览器 TTS、词卡、阅读设置

　　　　为什么做：不加服务器和音频文件，也能听、能查、能调阅读。

　　　　原来的方式：买带音频的课程或另装 TTS，音频还有体积与授权问题。

　　　　我的做法：朗读用浏览器 speechSynthesis，支持全文、点句、逐句跟读，不生成音频；词卡绑定目标词；字号行距存本地。

　　　　改进在哪：音频成本为 0，无下载、无 key、无授权风险。

　　（五）间隔复习与本地进度：没有服务器也能闭环

　　　　为什么做：让「今天读过」变成「以后还记得」，不依赖账号。

　　　　原来的方式：带账号的背词软件要注册联网；自己记表格容易断。

　　　　我的做法：首读后按目标词生成卡片（主线 59–60 张、补漏 57–58 张），卡片带回原句；间隔 1/3/7/16/35 天，四档评分，每日上限 120 张。进度存 localStorage（vocab.progress.v1），可导出/导入；看板按主线、补漏、中考三套统计。

　　　　改进在哪：不注册、不联网、不上传；换设备靠 JSON；复习页按到期日排序，显示今日已复习 / 120、卡片总数和连续天数，打开就知道该清哪些卡。

　　（六）零成本发布：62 个静态页面

　　　　为什么做：一个人能长期维护，随时可以停。

　　　　原来的方式：动态站需要服务器、数据库、域名和运维。

　　　　我的做法：Astro 纯静态，55 个短文页 + 7 个站级页 = 62 页；推送 main 由 GitHub Actions 发布；构建自动推导 base（项目仓库 /bei_dan_ci/，用户站点 /）；preview.sh 一条命令本地预览。

　　　　改进在哪：托管、构建、音频、存储零费用；无账号、数据库、埋点；停更后 62 页仍可用。

　　　　关键数据：

　　　　1. 篇数：55（主线 50 + 补漏 5）。

　　　　2. 目标词：3,242（2,953 + 289）。

　　　　3. 篇长：280–320 词；句长：8–14 词。

　　　　4. 每句目标词：2–4 个；词次密度：18%–22%。

　　　　5. 词表覆盖：2,953/2,953；289/289。

　　　　6. 全局审计：0 错误；页面数：62 页；成本：0 元。

二、TRAE 在开发中的具体帮助

　　这个项目的内容和决策都由我一个人做。我借助 TRAE 执行：我定标准、做取舍、判断什么算通过，让它把重复劳动和容易漏的核对写成脚本、页面和流程。

　　（一）词表核验：先证明「3,300 个词」不成立

　　　　问题：我按「柯林斯 3–5 星约 3,300 词」做预算，需要从 ECDICT 的 63MB CSV（770,611 行，MIT）清洗词表并验证预算。

　　　　我的判断：清洗后我发现实际只有 2,953 个头词（5★ 600 / 4★ 967 / 3★ 1,386），少 347。我没用低星词抹平缺口，否则对外就得把非星级词说成星级词。于是主线保持纯星级，另立 289 个无星级中考补漏词，标 stars=0、star_source=zhongkao，并承认中考词只有 1,547 个，比早期假设少 103。

　　　　我让它做的：

　　　　① 写清洗与校验脚本，生成三份词表 JSON 和两套账簿。

　　　　② 校验总词数、分篇词数、中考词是否全在前 22 篇、补漏是否与主线零交集。

　　　　③ 跑出星级分布和 take 标 1★、place 标 2★ 这类噪声。

　　　　结果：站点最终是 3,242 词、55 篇；主线 collins、补漏 zhongkao；页面固定标「非星级词」；validation.json 为 ok: true。后来写计划、做页面、跑审计，我都沿用这套标准。

　　（二）站点从零搭建：把内容变成 62 个可交互页面

　　　　问题：内容我能写，但站点要从零搭 62 页：55 个短文页、两条路线、四态、SRS、本地进度、部署，还要本地与 Pages 子路径都能跑。

　　　　我的判断：我选 Astro，不选 Next.js/SPA；不引后端和账号，进度只放 localStorage；音频用浏览器 TTS；base 不能手改。

　　　　我让它做的：

　　　　① 搭骨架和 55 个动态路由。

　　　　② 实现四态交互、8 题判分、SRS 四档与 120 张上限、导出/导入。

　　　　③ 封装 base，写 deploy.yml 和 preview.sh。

　　　　结果：构建 62 页；一条命令预览；推送自动发布；两种路径链接正确；全站无服务器、数据库和登录。

　　（三）55 篇受控写作：把「读起来顺」拆成可对账的指标

　　　　问题：每篇 57–60 个目标词，还要满足篇长、句长、密度、每句 2–4 个生词、词卡顺序、挖空回拼、答案唯一。人眼数一定漏。

　　　　我的判断：我给自己的标准是「看起来差不多」不算通过。每篇先过脚本再看读感，红灯不写下一篇；把「可记忆」拆成可计算约束。

　　　　我让它做的：

　　　　① 写 qc_check.py 核对单篇全部硬指标与素材一致性。

　　　　② 写 audit_all.py 对 55 篇做编号、结构、账簿、覆盖、分布、标题唯一性和 metrics 复核。

　　　　③ 报错定位到具体句和词。

　　　　结果：55 篇全过；全局 16,145 词、1,544 句、0 错误；3,242 词全有首现篇；词卡顺序与账簿一致。3 条提示、2 条备注保留，没有为全绿而删。

　　（四）全量审计与仓库发布整理：让仓库可以公开复现

　　　　问题：55 个 JSON、两套账簿、站点代码、部署工作流并存，任何漂移都会让「3,242 词」失真；仓库还要可复现，不能塞进 63MB CSV。

　　　　我的判断：我把数据当作唯一事实源；审计只把真错误算错误，题材重复、回译相似度低留作提示；源 CSV 不入库，只保留许可证与复现说明；v1–v4 留档。

　　　　我让它做的：

　　　　① 跑全量核对并生成报告。

　　　　② 补齐 README。

　　　　③ 检查 Pages 工作流的构建目录与产物路径。

　　　　④ 确认本地与线上 base 差异不影响链接。

　　　　结果：0 错误；稳定生成 62 页；换台机器按 README 可重建站点。

三、印象最深的一段经历：把 300 篇压到 50 篇

　　印象最深的不是某篇写得多顺，而是我推翻了自己最初那套看起来最「科学」的方案。

　　起点是每篇 11 个新词、约 300 篇短文。按这个设计，单篇负担最轻：每天读一小段，生词少，句式简单，任何一篇都不难。我当时认为这就是正确答案——把难度切碎，学习者就不会被吓到。

　　转折发生在算总账的时候。问题不在每篇轻不轻松，而在总量：300 篇意味着学习者要启动 300 次。多数人会在前十几篇就放弃，后面 280 多篇写得再好也到不了。

　　把难度平均摊到 300 篇，等于把「坚持」的成本放大了 300 倍。我作为作者也要写 300 次、维护 300 份译文和题目，这个结构对我自己同样不可持续。于是我做了个反直觉的判断：压缩篇数，哪怕单篇几乎全是生词，也可以接受。

　　最难的一环是：压缩不是把词表合并一下。篇数压到 50 之后，每篇要承载约 60 个目标词，我必须在「每篇像一个能读下去的故事」和「生词密度足够高」之间找平衡。我先试过最直接的办法：60 个词每个都塞两遍，保证复现。

　　结果两版初稿都退化成电报式短句，句子只剩「谁做了什么」，读起来不像故事，像词表换行。最后我把参数定下来：篇长 280–320 词、目标词密度 18%–22%、每句 2–4 个生词，每个词至少出现一次，复现交给后续篇目和 SRS。我据此把整份写作规则和计划重写到 v5。

　　这个决定的代价不只是改几个数字。它推翻了我已经写好的 300 篇方案，也推翻了配套的分配算法和页面结构：原来按 300 篇组织的目录、进度、每篇 11 词的节奏，全都要按 50 篇重做。等于把前半程的设计重做一遍。我既是作者，也是唯一的验收者，没有人能替我判断「这个代价值不值」，只能自己承担。

　　结果是 50 篇主线加 5 篇中考补漏，共 55 篇、3,242 词。第一篇样篇 302 词、28 句，目标词词次密度 21.9%，每句 2–4 个生词，读起来是一个连贯的星期六故事。之后 55 篇全部通过逐篇质检和全量审计，审计 0 错误。

　　这次转折让我后来的判断顺序变了：先算总账，再抠单篇。单篇难度可以调，总量结构一旦错了，后面每一篇都会替它还债。

附：这份作品目前是什么，不是什么

　　它是 55 篇可读、可背、可测的短文，3,242 个有来源标注的词，62 个零成本静态页面，一套能复跑的质检与审计脚本。它不是商业产品、账号平台或速成课；按一个人能长期维护的方式做，随时可以停。
